# Easy Data × AI 共学笔记｜第 2 篇｜场景识别与大模型 API

这是我在 Datawhale 上参与的 Easy Data × AI 共学项目的学习笔记，今天是 11 月 18 日，这是我的第 2 篇。

这次整理的是 Task 2 的三节课：道篇 P1《AI Agent 场景识别》、术篇动手课 D1《大模型 API 基础》和产业篇 I1《AI 原生数据库基础》。P1 和 D1 是 16 号学的，I1 是 17 号看的、18 号又做了一遍课后实践。

> **说明**：我的每次学习笔记，正文都是根据我课后的学习口述内容，用 AI 整理而成的。口述里的观点和经历都是我自己的，AI 只负责把口语整理成文字。

### P1：什么任务适合交给 Agent

P1 的完整标题是“找准 Agent 的用武之地”。这节课讲得挺有意思，主要回答一个问题：什么样的任务该交给 Agent，什么样的不该。

### 不是所有任务都需要 Agent

课程一开始就讲：并不是所有任务都需要用 AI Agent 来完成，尤其是一些比较简单的任务。

比如问“今天是星期几”这种问题，就没有必要用模型去答。因为模型是靠推理生成的，不是查询，反而有可能会出错。一些需要确定性答案的任务也不适合用模型——课程里举的例子是查退款政策这类固定答案的问题。这类问题要的是确定的结果，用模型反而可能出错。

所以这节课的核心就是“场景识别”：Agent 在哪些场景里才能发挥它最大的作用。

### 能力公式里新增了“流程编排”

这节课提出了一个关于 Agent 能力上限的公式。前几节课讲过 Agent 的能力等于数据质量乘以模型能力，这一节加上了“流程编排”。

按课程原文，公式是：**AI Agent 的能力上限 = 数据质量 × 模型能力 + 流程编排**。

流程编排，按我的理解就是“工作流”。工作流增加了确定性，因为它循着一条固定的流程走，这是确定的；而在工作流的每个节点上，再用 Agent 赋予一些创造力。这样就把创造力和确定性结合在了一起。

这是我的理解——我之前也了解过工作流，但课程里可能没有明讲这一层对应关系。

### 屋顶图：可行性的三个维度

课程还画了一个“屋顶图”，讲的是 Agent 项目的可行性，有三个维度：数据可得性、任务可定义性、流程编排的选择。这正好对应上面公式里的三个因子。

这部分内容比较抽象，我展开说说自己的理解。

**数据可得性**：Agent 要回答问题，答案存在哪儿？是在数据库里还是文档里？为了让这个概念不那么抽象，课程给了一个简单的验证方法：在项目立项的时候，随机列出 10 个你期望 Agent 去回答的典型问题，然后人工去找这些问题的答案，看能不能找到。如果大部分能找到，就说明这个项目可以让 Agent 去做；如果大部分找不到，Agent 就做不了。

按课程的说法，如果超过一半问题的答案数据都找不到，就应该先做数据建设，再启动 Agent 开发。

意思就是说，Agent 的运行必须要有数据。其实这门课从刚开头接触下来，就反复在讲数据。打个比方：**Agent 就像是个厨子，数据就相当于食材。厨子本事再大，没有好的食材，也做不出来好菜。**

**任务可定义性**：跟 Agent 协作时，任务必须明确、可定义，不能模糊。这也是目前限制很多人的一个约束，包括我自己在跟 Agent 协作时的体会。

难在哪呢？很多时候我们说不出来一个定义的标准——一个东西“好”的标准是什么？这个标准能不能量化、能不能测量？但确实有的时候，“好”是没有办法用一个可量化的标准拿出来测的。如果勉强要定标准，可能就得去找一个案例，或者一个相对已经成功的东西作参照——但找这个东西，又要花费大量人工。

我们用 AI、用 Agent 的时候，总希望啥都交给 Agent 去做，不想再做那么多前期的准备工作。所以课程里也讲到：想要确定性，就必须介入更多的人工或者客观的数据。不过随着模型能力的进步，对人的依赖可能会越来越低。这门课现在讲的内容，还是基于今年 3 月份的情况；估计到明年 3 月，对人的依赖可能就小多了——人可能只要提供一下数据源在哪，不用再去搬数据，告诉它一个数据地址，它自己就可以去读了。

所以，“定义正确的标准”这件事，目前还比较难，但后面可能会变得越来越容易。

### 我的反思：学这门课的意义在哪

在这里，我其实也在反思学这门课的意义。这门课更多还是在讲人应该怎么做，但随着技术的发展，对人的技术面要求可能会越来越低。我们现在想的是人应该懂一些技术，但后面可能对人的技术要求会越来越低。

我想，学这门课的意义可能就在这一段时间里：在模型的资料搜集能力以及对人的了解能力还没有完全达到完美的阶段——在这个所谓的“过渡期”里，人的这些知识和配合是有效的。这可能就是我学习它的意义。

### 什么问题适合交给 Agent

课程最后讲了“什么问题适合交给 Agent”，用了一张图，蛮清晰，可以让用户记住三类场景：

1. 语义理解的场景
2. 需要持续交互的场景
3. 需要调用工具的场景

在这些场景之外的任务，用工作流或者问答检索就可以解决了。

对于我们这种技术能力不算强的AI应用者来讲，其实这些判断都可以交给 Agent 去做——什么场景适合用 Agent、什么场景适合用工作流？当用户分不清楚的时候，可以直接问 Agent，让它来判断，我觉得都可以。

那人学一下有没有好处？也有。我们现在和 Agent 的协作，是从“指挥” Agent 的工作开始的。但现在或者将来，可能慢慢就不是你指挥了，而是你“请教”它——你只是请教，就不存在指挥了。

目前人可能还有一种感觉：“我在指挥 Agent 的工作，我同时指挥着几个 Agent”，好像还有这样的成就感。但其实将来，人就变成了去请教它：把你的需求说一说，只要说明白你的需求是什么，就行了。

这像个什么样的协作关系？有点像“会哭的孩子有奶吃”——你只要会说，它就可以给你想要的东西。

P1 的课后测验题我也都做对了。

### D1：学会用代码调用大模型

D1 是术篇的第一节课，一节动手课，要求写代码、配置参数、配置函数。

### 没必要自己写代码？

我个人感觉这些东西都没必要自己去写，也不太清楚为什么课程里还是要强调手动写代码。因为完全可以找一个大模型、找一个 Agent 来帮着写，然后再找另外一个 Agent 来帮它检核一遍就可以了。

自己写代码还是挺复杂的，要调试各种问题，输错一个字母就可能报错。我以前自己写过代码，被这个事折磨得很，很费时间。人工写会碰到各种报错，耽误的时间挺多，我觉得没必要为了反复排错浪费时间，只要知道原理就可以了。这是我个人的感觉，但不建议其他人这么做。

课程的说法是：动手不是为了背 API 文档，而是为了建立“用代码控制 AI”的工程直觉——“最好的学习，就是亲手实现它”。

### 组装一个智能体的五步

D1 最后讲的是怎么样去组装一个智能体。他画了一张图——我发现这一系列课程画的图都特别好记，特别让人容易记住。我觉得我可能也是一个“图片型”的选手，看图对图的记忆力会比较强一些；看视频的时候可能会走马观花，记不住。但把这些图结合文字，我觉得我的记忆力还比较强。

课后有一个模型组装的步骤，这张图挺有意思：

1. 安装 Python 环境；
2. 安装 LangChain——它其实就是一个调用大模型的工具；
3. 填入自己的大模型 API key；
4. 运行课程里面提供的代码；
5. 最后调用一个工具。

差不多这就是一个可以运行的智能体了。

### 打开了思路：不用 harness 也能调大模型

原来我对智能体的理解是：要在本机上安装一个 harness（比如 DSH harness），然后基于这个 harness 生成一个可执行的程序，程序里包含 API、skill 之类的东西，我们通过这个应用接口来调用它。我现在就是这么操作的。

但这节课讲到可以通过 LangChain 来调用大模型，这算给我打开了思路。原来我都是受限于“必须在运行智能体的机器上安装一个 harness 才行”。

当然，如果没有 harness，运行的智能体理论上应该会更小巧一些，但我没做过，不知道它的可用性怎么样。成熟的 harness 会更成熟一些，运行的时候可能会更稳定——这理论上我也没有做过测试。

总的来说，D1 是有一定的实操价值的，也给我增长了一些见识。虽然原来自己也在搞一些智能体，但一直不明所以，现在算知其所以然吧。

### 还是那个问题：知其所以然的价值在哪

回到上一节 P1 里面的问题：我不知道这个“知其所以然”的价值在哪儿，有没有必要知其所以然——我有时候也在思考这个问题。

### I1：Agent 背后的数据底座

I1 是产业篇的第一节。这节课我的观感和前两节完全不同：开头的基本概念还能看懂——大模型负责推理，数据负责保存结果的存储、提供推理所用的材料；但后面的内容出现了太多新名词和专有术语，我就看不下去了。技术原理、工作流程都过于抽象，我既理解不了它的工作原理，也理解不了它的工作流程，也想不明白它讲这些底层技术内容的目的是什么。

我学这门课的目的很明确：一是更好地了解 Agent 的运行原理；二是协作时了解它的长处和短处，更好地与它协作。这些非常底层的技术内容，我无法理解对我的将来应用有什么价值。纯技术那部分我没看，基本的逻辑我是掌握的。

和 AI 助手讨论之后，我对这章的结论是：I1 的技术细节是写给要自己搭数据系统的工程师的，不在我的需求路径上，硬啃没意义——术语这种东西，不用它根本记不住，硬记住了隔一天就忘，记的价值都不知道在哪。这章对我来说最值钱的就是一句话：**Agent 的每个能力（RAG、记忆、工具调用）背后都压着一层数据，这层数据管事实、权限、恢复。**

拿这句话对照我自己，我原来理解的“事实、权限、恢复”和课程说的有出入，纠正了两个：权限不只是 AGENTS.md 管的 Agent 行为权限，还有数据权限——哪个用户能看到哪条数据；恢复不是记忆，是崩了之后已确认的操作不丢（类比 Word 自动保存、游戏存档）。

我还想过一个问题：如果我要搭个数据系统，能不能用自然语言和 Agent 协作，让它帮我搭？我觉得 Agent 的能力肯定比一个普通数据库工程师强。讨论后的结论是：行，中小规模 Agent 完全够格；但工程师的核心价值不在写代码，而在知道“该建成什么样”——数据量多大、要不要权限过滤、写进去的数据多久后必须能查到，这些得人告诉 Agent，说不清的委托不出去。这正好呼应 P1 的“任务可定义性”。

### 用自己的 Agent 工作流做一次数据底座评审

按课后行动的要求，我拿自己日常的主力体系（Codex 为主，ZCode、DSH 等 7 个 Agent，两台电脑）做了一次“数据底座评审”。要点：

- **事实**：所有项目记录、会话记录全在 Codex 里，离了它我就完全没办法工作。7 个 Agent 里高频 3-4 个：Codex、ZCode、Claude，有时 Kimi（桌面版）；WorkBuddy 和 opencode 用得少。
- **记忆**：两层。Agent 自带记忆之外，我自己搭了一套：每晚下班前在主机和笔记本的 Agent 里跑“同步保存”skill，检索今天所有项目的会话记录，提炼要点形成工作汇总，同步存到工作区和Obsidian（Agent 后缀区分）；再把这些汇总集中到笔记本 Codex 二次汇总——Codex 桌面版就变成了解所有项目进度的完全个人助理。这套机制也写在所有 agents.md 里。
- **任务状态**：任务跑一半崩掉（模型调用错误、额度到）是常事。我的办法是新起一个线程，让它先找原线程的会话记录，找到再继续。能按日期定位，因为工作记录以天为单位保存。
- **恢复**：本机 + Obsidian + 异地三层。Obsidian 在本机；异地是 OneDrive 免费 5G（文档脚本为主，图片视频体积太大不同步）+ Codex 会话记录推 GitHub 私有仓库。“这就是我的命，能找回来。”我不信纯云端——Codex 付费版送云存储全存云上，但我本机一定要保存，云端只做同步。
- **权限**：私有仓库和 OneDrive 只有我自己能看到。公司员工通过站台调用的那些 exe（skill+API 绑定），skill 只能访问它约定的参考/模板文件，访问不到我本机其他数据；公司平台跑在服务器上，转不到我本机。公司目前还没有完全独立、能连知识库回答所有问题的 Agent——能处理具体任务的有，完整任务的还在构思中，这也是我技术学习的原因。
- **多源同步的代价**：两份工作记录有重合时，如果只说了重合的地方、没说不一样的地方，它可能记错，需要纠正。
- **收益与风险**：好处是数据尽量全在本地、多地保存、目前免费；坏处是免费空间做不了全量备份，数据量到了一定规模可能要考虑付费服务。

做完这道题我的感受：课程里说的 Fork/Diff/Merge（给会写数据的 Agent 一个隔离试验、人审过后再采纳的机制），我天天在干——“任务崩了新线程找原记录再继续”“记错了人工纠正”就是同一个纪律，课程只是给它起了个数据库名字。

另外补充一段自己的经历：Codex 在 6、7 月份出过几次灾难性事故。当时 Codex 接的是 DeepSeek 模型，在 Power（PowerShell）里语音识别错误，识别不出中文就会向上识别，当时执行的是一个删除任务，结果递归向上，最严重的一次把整个 D 盘全删了，损失很大。7 月份之后我做了异地备灾。奇怪的是，做了备灾之后反而没再出过这种问题。
