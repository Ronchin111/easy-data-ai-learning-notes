# Easy Data × AI 共学笔记｜第 3 篇｜Agentic RAG 产品设计与向量数据库

这是我在 Datawhale 上参与的 Easy Data × AI 共学项目的学习笔记，今天是 11 月 19 日，这是我的第 3 篇。

这次整理的是 Task 3 的两节课：产品篇 P2《Agentic RAG 产品设计》和产业应用篇 I2《向量数据库与 RAG》。P2 是 18 号看完的，I2 是 19 号看完的，两节课连着学下来，正好是"产品设计视角"和"技术实现视角"看同一件事。

> **说明**：我的每次学习笔记，正文都是根据我课后的学习口述内容，用 AI 整理而成的。口述里的观点和经历都是我自己的，AI 只负责把口语整理成文字。

### P2：Agentic RAG 和普通 RAG 的区别

这个 Agentic RAG 和普通的 RAG 有啥区别呢？课程里面讲，普通的 RAG 是一个写死的工作流，而这个是闭环的，可以自我迭代。但具体怎么做呢？其实我也没有去看详细的技术细节，我没看懂。

#### 检索不只是向量检索

这篇课程从"检索"讲起，它本来的英文单词的意思是"检索增强生成"。可能原来"检索"指的是向量检索，但从广义上讲，检索包括很多种，不只是向量检索，所有获取外部信息都叫检索。

不过这个对我的理解来说，我觉得也没有什么特别大的意义，因为我原来对这个也没有什么认知上的偏见。

#### 技术细节要学到多细？我问了 AI

我对这篇课程的总体印象是，它还是讲了很多的技术。虽然这是一个产品篇，是给产品经理看的，但还是有很多内容偏技术，不知道后面的"术篇"或者"产业应用篇"里面会不会更偏技术。

我就这个问题，和 Claude Code 认真聊了一下。我说，是不是非要去了解这些技术细节才可以搭好一个知识库？如果我跟 Agent 协作，可不可以就搭好这个知识库？

结论是：只要能知道 RAG 的步骤，能判断 Agent 产出质量的好与坏，那基本上就可以和 Agent 协作了。那些技术细节其实没有太大的必要去了解得那么细。

既然它这么回复我，我心里的石头就落定了，感觉这相对来说就有价值。否则，我会觉得学习曲线太陡峭、成本太高。那我这些技术细节就略过了。

#### RAG 的六步流程

这节课第三部分讲了一个完整的流程：

1. 数据准备
2. 问题理解
3. 搜索召回
4. 融合重排
5. 生成
6. 评估

这 6 个环节，我是有必要了解的。前 3 个环节跟数据和检索有关，后 3 个环节跟模型和生成有关。

#### 数据准备的七个步骤

"数据准备"呢，就是要把什么样的数据接入到知识库里面去。这些数据都包括哪些不同类型呢？不同类型的数据可能有不同的解析方式，比如 PDF 和 HTML，可能就需要用不同的方式去解析它们。

数据进来之后，里面肯定混杂了一些没有用的数据，要把它清洗掉。比如会不会有重复的？会不会有什么页眉、页脚、页码这些没有用的信息？会不会像 PPT 或者 PDF 那样，有一些现成的企业模板？要把这些模板信息都去掉，只提取其中有价值的文字，这就叫清洗。清洗完了之后要切分，按段落、章节、问答切分；然后要做增强，增强就是给它加标题、章节、别名、版本号等等；接着建索引，索引很有价值，因为有了索引之后它才能被搜索到；最后还要考虑这个该怎么更新。

其实这里面说起来有这么多步骤，有 7 步，但其实我没有操作过，或者我操作的时候都比较简单。

#### 我和 RAG 知识库打交道的经历

我最早接触到 RAG 知识库是在"扣子"（Coze）的时候。那时候如果要做问答智能体（也就是问答工作流），肯定要给它配个知识库。当时就是做个测验，给它 10 份、20 份文档，让它自己去做解析、清洗和切分。它会给你提供几种切分的方式，你自己去选就行了：是按段落切，还是按语义切，还是按问答对切。但是我也不清楚这些切分有什么区别，建索引之类的，我一般就是让 Coze 里面自带的数据库工具去弄。

弄完之后，我会在实际应用时，通过人工提问的方式看它回答的结果怎么样。根据回答得好不好，我再去修改。后来发现这种方式还是挺慢的，效果也不好。去年用 Coze 的时候还都是人工在做，当时感觉太复杂了，太费时间，太耗人力。

再后来，今年 5 月份我参加了市数据局的"人工智能+政务"大赛，也是做一个问答智能体。这次做的时候，我就完全不需要人工去做了，全部是用 Agent 去做的。我直接用 Agent 去提交，快速去试，然后快速用 Agent 去做评测——其实就是个评测集嘛。之前没见过评测集，都是人工去测，测完之后再人工去判断哪些好、哪些坏。

其实做一个问答智能体，最烦、最复杂的就是这个知识库。其他的那些编排，比如用户查询，然后做意图分析路由，再路由到不同的知识库里面进行召回，召回完了之后再交给大模型去生成。因为是政务智能体，它面对着不同的场景或部门，在回复时需要接入不同部门的回复模板，然后再综合生成一个最后的答案给用户。当时就是这么做的，都是 Agent 做的，还得了第 3 名。

所以我觉得现在知识库的话，像 RAG 这些东西，我个人感觉完全没有必要自己手工去操作，可以依靠 Agent 去操作，只要知道这个步骤就可以了。

融合、重排等等上下文组织生成，知道就可以了，这些东西只是看过了解一下就行。

#### 三层归因框架：答错了怎么破案

第 5 部分讲了一个东西，讲得也挺有意思，这就叫"三层归因框架"。

假使 AI 对用户的提问答错了，要进行归因分析"破案"的话，基本上答错后可能在三个方面出问题：

第一，数据层：你给的数据不足，或者给的数据不全。第二，模型层：模型回答出错了，出现了幻觉。第三，业务层：你回答的方式具体到应用场景里面，让用户不能理解。

从课程里面讲，60%~80% 的问题出现在数据层，模型层出现幻觉的概率不大，只有 10%~20%。也就是说，大部分问题出在数据这块，人工只要知道一般是哪些方面容易出问题、出了问题该怎么解，以及该怎么去指挥 Agent 去解决就可以了。

具体排查方法：如果问题出现在数据层，要去检查一下数据的准确性、全面性，以及数据库里面切分索引这些东西做得有没有问题。如果问题出现在业务层，就要去看它回答的方式。如果太专业了，就要去检查一下大模型的提示词，让它修改一下提示词，通过调整表达方式基本上也能解决业务层面的问题。

#### 课后行动：拿一个真实案例做归因

课后行动要求收集最近几条"AI 答错了"的反馈，用归因决策树逐条判断。这题跟 Task 1 的思考题有重复，我就拿了一个刚踩的坑来做。

**案例：Kimi 写项目方案书，三版名词混串。**我在 Kimi 上让它帮我写一个项目方案书，给了它一份阅读资料。方案书前后写了两三版：第一版的名词叫 A，第二版叫 B，第三版叫 C。它在写第三版的时候，里面的名词就混了，有的地方用 A，有的地方用 B。

我的判断：现在的模型会自己把聊天记录保存下来，再做报告的时候，就会受到前面记忆的污染。之前说的是"知识库"的信息会遗忘，但现在出现的问题是知识库的信息会互相污染。这不属于 RAG，而是模型自身的记忆体系——它的记忆体系里没有按时间线去做。我用的是不错的模型（Kimi 3.1 Pro），所以我觉得这可能就是模型本身智力的问题。目前还没有什么好的解决办法，只能跟模型沟通去修正，人工告诉它原来的哪些记忆不要使用了。

按课程归因树走一遍：知识库里有没有正确答案——有，最新版该用的名词就在会话里；检索到了吗——检索到了但检索错了，召回的是第一、二版的旧名词；回答和检索内容一致吗——它对"该用哪一版"没有判断，忠于了全部旧证据而不是最新证据；业务层——不搭界。**归因结论：数据层问题的变种——记忆污染。**和 AI 助手讨论后还确认了一点：这个现象行业里叫"上下文污染"，不全是模型智力问题——模型越好越会"忠于"上下文里的一切，包括过期的部分，它没有义务自动知道"第二版已作废"。工程上的解法就是两种：开新会话隔绝旧上下文，或者在提示里显式作废旧版。我说的"分批各取有用内容"，对应的就是人工做记忆筛选后喂干净上下文。

归因统计：1 个案例，数据层。跟课程预告的"大部分问题出在数据层"一致。

### I2：向量数据库与 RAG

#### 难度直线上升，看不下去了

I2 这节课，我的观感跟 I1 差不多：整篇内容从课前导读、基础，一直到 Task 3，知识难度是成直线上升的，中间都没有过渡，很多词语也没有解释。

课前导读里说"只要具备一点点的 Python 基础就可以来学这门课"，但实际上里面很多内容都是跳跃性的，没有循序渐进。对于初学者来讲，其实是没有办法跟进这门课程的。如果初学者想理解里面的内容，必须要阅读大量的课外教材，而且要自己去检索、查询、掌握里面的名词，才能看懂文章的意思。

#### 有没有必要了解这么专业的东西

我只是觉得，有没有必要去了解这些特别技术性的东西？比如什么叫 ANN，什么叫 KNN？"向量化 embedding"这个词我是看过好几次，在这节课里面他也没有明确讲呀，什么叫向量也没有完全讲清楚，对我来讲，我也没听懂。

我之前了解过的向量化的意思，就是说他会把文档里面的这些字符保存在知识库里面，但他肯定不是以字符的方式保存的，而是以一种叫"向量化"的方式。什么叫向量化？我不知道，也不清楚，但意思就是他把它保存下来，不是以字符的方式，也不是以什么字节、比特的方式保存。他是把字符做了一个向量化，距离什么 9，我是没法理解的，那可能就比较技术一些。

而且在我实际应用的时候，我也不清楚为什么要了解得这么多、这么专业。我是在智能体的应用场景里，不知道学习这些相对来说非常底层、非常专业的词，它的用处是什么？

因为我肯定是用 Agent 来指挥 Agent 工作的。比如说我要建一个 RAG 向量化什么的，我肯定是指挥 Agent 去帮我做，跟 Agent 去协作，让 Agent 提供一个成果，最后由我来验收。我验收的时候，就看这个知识库在使用时回答的准确率高不高，通过结果来验证。这里面的过程到底怎么做的，其实我都是让 Agent 帮我把握的。我觉得我也没有这么多的精力和时间，去把这么多的东西学得那么透彻。在这个时代，花这么多时间来学这个东西，其实是不是一个聪明的做法？这会把自己的精力完全锁在一个很微小的领域里面。

因为我们更多还是要利用大模型、利用 AI、利用 Agent 来扩展一个人的能力边界，然后能胜任在不同的领域里面去做事。所以在某一个专业领域里面投入这么多时间去学习专业知识，我现在还没有想清楚这个价值到底体现在哪儿。

比如很多底层的专业东西，像京东的 Agent，它对这些技术的理解肯定超过 99% 的人，我在学，能学到那 1% 的人的水平吗？比如说，我花了 10 个小时去学，最后节省的时间就一个小时，那我就学了干嘛呢？

因为我们属于是应用，不是研究底层技术。我怎么可能去研究一下，然后研发出一个更好的向量技术，或者更好的 RAG 检索技术？我又不是做那个活的人，对吧？

举个例子，我就是个厨子，我就知道买一把好一点的菜刀，切起来很快很利索，而不是我去研究这把菜刀是怎么做出来的、用什么材料、用什么锻造工艺。研究那玩意儿对我自己切菜有帮助吗？

#### 和 AI 助手讨论后，这些疑问解开了

我最后还是把这个疑惑拿出来跟 AI 助手辩了一轮，讨论下来结论是这样的：

**课程为什么写这么深？**这门课的预设读者是"想入行做 AI 应用开发的人"——要自己搭、自己选型、自己调参的那种。产业篇在课程 README 里本来就标的是"按兴趣深入"。课前导读那句"一点点 Python 基础就能学"跟实际难度不匹配，我"难度直线上升、没有过渡、名词不解释"的观感是准确的——不是学不动，是课程对读者的假设错了位。另外还有"知识诅咒"：作者天天跟这些词打交道，已经忘了"不懂 ANN 是什么感觉"，于是默认读者也懂。向量化是全篇最核心的概念，课程却跳过没解释——这是课程的失败，不是读者的。

我还追问了一层：这个时代，下一代工程师为什么还要手敲代码学这些？讨论的结论：不需要。课程 D1 自己都写了"推荐用 AI Agent 代替手动安装"——它自己都不信自己的"亲手实现"哲学，只是课是 3 月写的，身体没转过来。"手敲一遍"对入行者还有一点校准信任的价值（亲手跑通过失败案例，才知道 Agent 报告里哪句话在吹牛），但我不需要这个校准，因为我已经在用结果验收了。而且说到底，我实际做的事（政务智能体、公司站台、Coze 知识库）就是 AI 应用开发，只是用自然语言做、别人用 Python 做——我在读者群里，只是课程没按我这类读者的方式写。

**留下的三句话。**I2 里值得留在脑子里的就三句（概念定位级，成本 10 分钟不是 10 小时）：

1. 向量化（embedding）就是把一段文字变成一串数字，数字之间的"距离"代表意思的远近——意思越近，距离越近。
2. 它的好处（课程没讲的那句）：字符搜索只能找一模一样的字——"退款政策"搜"退货规定"就是搜不到；向量检索按意思找，能搜到。我之前悟到的"向量把意思相近的内容联系在一起、不从字符层面联系"是对的，就差这最后一步"所以能干嘛"。
3. ANN 和 KNN：KNN 是精确找（小库可以），ANN 是近似找（库大到一定程度，快比准重要）。知道这一个是"规模问题"就够了，公式不用看。

#### 思考题里有两道"我的题"

课后思考题 6 道，大部分是技术题（距离函数怎么选、KNN 为什么是基线这类），我拍板跳过了。但有两道不是技术题，我用我自己的话答了：

**第 5 道：检索质量提升了，最终答案质量为什么可能没跟着提升？**我的答案：最终答案质量由几部分组成——从知识库检索出来的，加上用户的 prompt，再交给模型生成。RAG 分三步嘛，检索、增强和生成，那问题就出在"增强"和"生成"这两块没做好。生成依赖大模型，可以换更好的模型；那增强靠什么提高？我问了 AI 助手，答案是：增强没有"换更强模型"这种一键升级，它是纯工程环节，靠调规则——过滤（权限、时效、版本，我的 Kimi 案例就是这步坏了）、去重、排序（相关的放前面，模型对长上下文中间的内容容易忽略）、限量（别把半个库塞进上下文）、格式（分节加来源标注）、重排（先便宜粗捞、再精排打分）。（AI 助手还帮我确认了一点：我在政务智能体里做的"路由召回、接部门回复模板再综合生成"，就是亲手做过的上下文组装，又是名字没对上。）所以检索只是三层归因的数据层，组装和生成落在模型层、业务层——数据层修好了，后两层照样扣分。Kimi 那个案例反过来正好验证：料都在（检索没问题），坏在组装时把三版旧料全塞进去了。用厨子的话说：生成=换厨子，检索=买食材，增强=备菜——厨子再好也救不了烂备菜。

**第 6 道：专用向量数据库的收益，够不够覆盖新增的系统成本？**我的答案：这题没法空对空回答。收益一般就是检索质量，好处是省用户时间、提高体验；但成本要去衡量：时间成本节省了多少、体验提高的价值是什么。没有对比衡量，就没法回答。和 AI 助手讨论后确认：这就是标准答案——课程自己第 12 节也说选型"没有脱离场景的绝对优劣，由真实工作负载决定"。落到我的场景（中小规模、文档百篇以内的团队知识库），结论就是现在不用专用向量库，统一方案优先。

课后那个实验（30 篇文档跑检索对比、统计指标、调参）我不做——那是一整套工程实验，将来交给 Agent 跑，我验收结论就行。
