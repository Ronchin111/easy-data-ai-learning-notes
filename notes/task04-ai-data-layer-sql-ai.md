# Easy Data × AI 共学笔记｜第 4 篇｜从课程检索到 SQL 调用 AI

这是我在 Datawhale 上参与的 Easy Data × AI 共学项目的学习笔记，今天是 11 月 26 日，这是我的第 4 篇。

这次是 **Task 4**。我学了开发者篇 **D2《AI 应用的数据层》** 和产业应用篇 **I3《SQL × AI —— AI Functions 的设计与执行》**。

> **说明**：我的每次学习笔记，正文都是根据我课后的学习口述内容，用 AI 整理而成的。口述里的观点和经历都是我自己的，AI 只负责把口语整理成文字。

### Agent 查资料，得先想清楚资料怎么放

D2 有理论也有实操。特别技术性的部分我先跳过了，倒是开头那个金字塔我记得很清楚。底下是数据，中间是 RAG、Skill、MCP 和 Memory，上面是 Agent。之前学的是 Agent 怎么调用工具，这节课让我开始想，工具接到请求以后，究竟去哪里找数据、怎么把数据找回来？

我一开始以为，资料进数据库时已经向量化了，那我再提问，为什么还要做一次向量化？和 Agent 聊完，我才把这两步分开。入库时把资料切成段，每段变成一组数字存起来。提问时，库里那些段不用重新算，只把这次的问题也变成向量，才能和已经存好的资料向量比较。系统找到相关段落以后，再把原文交给模型。

切分这件事，我原来觉得交给工具就行了。现在至少知道，整篇放在一个向量里，很多主题会混在一起。切得太碎，又可能只找到半段解释。切成多少段只是一个数字，最后还是要看搜出来的那一段能不能说明白问题。

### 三个厨房，我记住的是各有分工

课文里“三个厨房”的故事比较形象。向量搜索能应付换一种说法的提问，全文搜索能照顾错误码、函数名这种少一个字都不行的内容。关系过滤我原来没看懂，换成自己的例子就明白了：我只想查 Task 4 的 D2，或者只查某个版本，就先把可以搜的资料范围限定住。

seekdb 把这些能力放在一起，对我来说最大的用处是少维护几套系统。至于实际能不能找到想要的那一段，我还是想自己试一下。

### 我真的把一节课放进数据库试了试

我让 Agent 帮我把 D2 课程原文切成 44 段，存到本地 seekdb，再在 PowerShell 里问问题。最开始问“为什么不能把整篇文章存成一个向量”，我没有在返回结果里找到该看的解释。改了搜索方式以后，有的题找到了，有的还是不行。前前后后折腾了七十几分钟，这是我对整个搭建、试用和调整过程的印象。

我当时就怀疑，是不是向量模型选得不好。后面的对照用的是同一份课文、同样的 44 段和 8 道课内问题。原来的 MiniLM 在这 8 道题的前三条结果里都没找到完整证据，换成中文 BGE 后找到了 4 道，我最初那道题排到了第三。原生全文搜索在这组题上找到了 5 道，全文和 BGE 融合后是 4 道。这组结果让我对“换模型能不能解决”有了更具体的判断。模型会影响检索，但有些片段输入太长被截断了，两种模型的输入设置也有差异，眼下还不能把效果全归到模型上。

我本来想把它做成一个网页学习助手，让同学们能问课程问题，也能记笔记和学习状态。试了一圈，我觉得只做一节课的问答，直接把原文交给模型读可能更省事。后来用同一节课的全文做了个小样，8 道课内题都给出了能核对的出处，2 道课内没有依据的问题也说明了本课没讲。这个结果只覆盖这一节课的这批题。我暂时没有继续用 seekdb 做网页，也没有因此否定它做跨课程检索的价值。对我来说，先试清楚一件事有没有必要做，比先把产品搭起来重要。

### I3 代码看不懂，我先把工单的流程讲明白

I3 确实偏难，我读过一遍，很多代码和最后的总结还是没看懂。贯穿全课的客服工单我能理解：收到一个新问题，先找到相似的历史记录，从里面挑出最有用的几条，再根据这些记录写一份回复草稿。

照着这个例子，四个函数的分工就容易记了。**AI_EMBED** 把文字变成向量，帮助系统按意思找资料。**AI_RERANK** 给已经找出来的候选再排一次序。**AI_PROMPT** 把问题、材料和写作要求组装好。**AI_COMPLETE** 才调用模型生成回复。先找到证据，再让模型依据证据回答，这条流程可以用来做 RAG。如果只是把一份工单归类或者写个摘要，单用生成也能做。

还有一点是我复习时才弄明白的：SQL 可以先限定数据范围，模型只处理选出来的这部分。一条 SQL 要是让模型逐行处理，背后可能发出很多请求。所以课上说“问题向量只算一次、只给少量候选重排”，其实是在控制这一步会花多长时间、用多少模型调用。我还没跟着做 I3 的工单实验，下一次跟 Agent 实践时，我想先看清每一步输入和输出，再决定哪些步骤值得接进自己的应用。
